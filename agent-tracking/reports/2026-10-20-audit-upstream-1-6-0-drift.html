Summary

Upstream 1.6.0 added the duplex mode (GPT-Live), new OpenAI realtime and GPT-6 models, ElevenLabs v4, Sarvam bulbul:v4-flash, and removed gpt-5.1 and gpt-5.4-nano. The proxy mirrors these allowlists locally and has none of the 1.6.0 changes. Gemini and STT lists and assistant_end_call_webhook are already current.

Q-001 High Missing mode: duplex rejected everywhere

src/assistant/assistant.rules.js:121-127; src/assistant/assistant.validation.js:207-240; src/core/db/schemas/assistant.model.js:14; src/assistant/wizard.service.js:130,260

Evidence. normalizeMode throws "assistant_mode must be one of 'pipeline', 'realtime', or 'cascade'" for duplex (run and confirmed). PROVIDER_COMPATIBILITY and COMPATIBILITY_MATRIX have no duplex row, validateProviderCombination answers "Invalid mode", the Mongoose enum for llm_mode has three values, and the wizard allowed_values list has three.

Why it matters. Users cannot create or switch to upstream's fourth mode. Worse, if validation were bypassed, create calls upstream first and then fails on the local enum, leaving an upstream assistant with no local mirror row.

Fix. Add 'duplex' to normalizeMode, the Mongoose enum, both compatibility tables (provider openai only, gemini rejected) and the wizard. Treat duplex like realtime for 'no TTS/STT stage' (see Q-002).

Q-002 High Mode checks hard-code 'realtime' as the only mode without a speech pipeline

src/assistant/assistant.service.js:97; src/assistant/assistant.update.js:199,229,260,285,294; src/assistant/assistant.rules.js:321-330,365-378

Evidence. Every branch that decides whether TTS/STT apply tests mode !== 'realtime'. For duplex that means create demands assistant_tts_model + assistant_tts_config (assertTtsPairProvidedForMode), and update inference turns any TTS/STT edit on a duplex row into mode 'pipeline' (inferTargetModeForUpdate returns 'cascade' or 'pipeline' only). Upstream: duplex ignores TTS/STT, keeps stored ones, and does not strip them.

Why it matters. A duplex assistant cannot be created without bogus TTS fields, and an edit of its stored TTS config silently flips it to pipeline. stripPipelineFields must stay realtime-only: upstream keeps stored TTS/STT for duplex so switching back needs no re-send.

Fix. Introduce one helper (for example hasSpeechPipeline(mode) true for pipeline and cascade) and use it in all six places. Decide the inference rule for TTS/STT-only edits on duplex and realtime rows (keep current mode instead of forcing pipeline) with the owner.

Q-003 High Duplex field rules and refusals not implemented

src/assistant/assistant.validation.js:297-350 (validateModelParameters); src/assistant/assistant.rules.js:130-137

Evidence. validateModelParameters sends every non-cascade mode to OPENAI_REALTIME_MODELS, so model gpt-live-1 would be refused. backend_model, backend_instructions (max 4000 chars), duplex voices (beacon, cedar, cinder, marin, stone, vesper) are unknown. Not refused: enabled assistant_greeting_audio, filler_words true (sanitizeInteractionConfigForMode only forces false in realtime), temperature. Knobs must be checked against backend_model, not model. Switching into or out of duplex must clear the stored llm_config unless a new one is sent (also in the local mirror).

Why it matters. Wrong configs are stored and fail at upstream with a 422/400, or reach a call that cannot speak a greeting.

Fix. Add a duplex branch: model gpt-live-1, voice list, backend_model in the reasoning list, instructions length, refusals as 400, knobs via unsupportedKnobReason(backend_model). Mirror the config reset in buildLocalUpdateFields.

Q-004 High OpenAI model lists stale in both directions

src/assistant/assistant.rules.js:20-26,58-69; src/assistant/assistant.validation.js:44-64; tests/assistant/validation.test.js:79; scripts/check-assistant-payload.js:146

Evidence. Confirmed by running: validateModelParameters('cascade','openai','gpt-6-luna') and ('pipeline','openai','gpt-realtime-2.1') both return isValid false. gpt-5.1 and gpt-5.4-nano are still accepted though upstream 1.6.0 rejects them (retire 2027-04-01) and REASONING_MODELS / REASONING_TOOL_INCOMPATIBLE still list them.

Why it matters. New models unusable through the proxy; retired models still accepted and then 422 upstream.

Fix. Realtime: add gpt-realtime-2.1, gpt-realtime-2.1-mini. Cascade: remove gpt-5.1, gpt-5.4-nano; add gpt-6-luna, gpt-6-sol to cascade and REASONING_MODELS (reasoning family, GPT5_GENERATION, no temperature). Keep gpt-5.4-nano out of REASONING_TOOL_INCOMPATIBLE for new writes but see Q-005.

Q-005 High Removing retired models naively locks users out of editing stored assistants

src/assistant/assistant.update.js:159-181; src/assistant/assistant.validation.js:339-356

Evidence. updateAssistant validates the merged stored row on every PATCH, and validateModelParameters re-checks the stored llm_config.model against the cascade allowlist even for a rename. Once gpt-5.1 / gpt-5.4-nano leave OPENAI_CASCADE_MODELS (Q-004), any PATCH to an assistant that stores one returns 400. Upstream does this too, but you chose reject-new-allow-repair.

Why it matters. Users with stored retired models could not edit the assistant, including the edit that would fix the model.

Fix. Check the model allowlist on the merged row only when the request touches assistant_llm_config or assistant_mode (as assertLlmModelAllowedInMode already is). Reject a retired id only when sent in the request. Note: upstream still refuses the PATCH itself, so the proxy cannot fully repair; document this and ship the migration script (Q-009).

Q-006 Medium PATCH assistant_llm_config replaces the local mirror instead of merging

src/assistant/assistant.update.js:40,100-130; src/assistant/assistant.update.js:162-167

Evidence. Upstream (and the validation view two lines earlier) merge assistant_llm_config key by key and null removes a key. buildLocalUpdateFields copies updateData.assistant_llm_config wholesale into llm_config via $set, so a PATCH naming only model drops the stored provider, voice, api_key and knobs from the mirror, and a null stays as a stored null. The next PATCH is then validated against a truncated stored row, which defeats the stored-knob check the tests at update.test.js:173 rely on.

Why it matters. Mirror drifts from upstream; knob and voice checks silently stop seeing stored values.

Fix. Build the mirror value with the same merge used for validation (spread stored then request, then delete keys whose value is null); replace outright when leaving realtime or crossing duplex (Q-003).

Q-007 Medium Update crashes with TypeError when the assistant has no local mirror row

src/assistant/assistant.update.js:142,162

Evidence. existingAssistant is null for assistants created directly upstream or before mirroring; line 162 calls existingAssistant.toObject() without the optional chaining used elsewhere in the same function (lines 144, 199, 207). Suspected, from reading; not run.

Why it matters. PATCH returns a 500 for such assistants. Compare the 404 path in webcall.service.js.

Fix. Return a 404 (as webcall does) or fall back to {} and skip the mirror write; add a test.

Q-008 Medium ElevenLabs TTS rules out of date

src/assistant/assistant.rules.js:254-260; swagger.yaml:4164

Evidence. ELEVENLABS_TTS_MODELS lacks eleven_v4 and eleven_v4_turbo. voice_settings are not gated per model: upstream 422s settings a model ignores (eleven_v3 reads only stability; v4 reads stability and similarity_boost; speed on v3/v4 rejected). eleven_monolingual_v1 / eleven_multilingual_v1 are rejected upstream (already absent locally).

Why it matters. v4 models are rejected locally with a 400; ignored settings reach upstream and 422 with an upstream-worded error.

Fix. Add the two models, and either mirror the per-model matrix from models.md or pass voice_settings through and let upstream answer (owner's trade-off per CLAUDE.md section 2: strictness vs passthrough).

Q-009 Medium Sarvam TTS: model field and bulbul:v4-flash rules missing; speaker check hard-codes v3

src/assistant/assistant.rules.js:277-315; src/assistant/assistant.validation.js:386-405; src/integration/providers.js

Evidence. assertSarvamSpeakerAllowed only knows the 30 v3 speakers and its error says 'bulbul:v3'. assistant_tts_config.model (bulbul:v3 default | bulbul:v4-flash) is not read, so a v4-flash assistant with speaker shubh_hi_customer is refused locally. Also missing for v4-flash: 224-speaker roster, pace 0.5-2.0 (v3 0.3-3.0), sample rates 8000/16000/22050/24000 only, temperature rejected, IN22 language codes (as-IN, ur-IN, ...) accepted only on v4-flash and a 422 on v3.

Why it matters. A new upstream TTS model cannot be configured through the proxy.

Fix. Branch the speaker, language, pace, rate and temperature checks on tts_config.model. The 224-name roster is data: keep it in one module (for example src/assistant/sarvam-speakers.js) or pass the speaker through for v4-flash (owner decision).

Q-010 Medium No migration or audit coverage for retired models in the local mirror

scripts/audit-assistant-models.js:14-31

Evidence. DEAD_LLM_MODELS lists the 2026 retirements but not gpt-5.1 / gpt-5.4-nano; the audit script is read-only and there is no move-to-replacement script (upstream ships migrate_retired_models: gpt-5.1 to gpt-6-sol, gpt-5.4-nano to gpt-6-luna, including duplex backend_model). Per CLAUDE.md section 6 migrations ship with the change.
